# v1.0 — Bancada de instrumentação para dataset de qualidade de energia

Este documento descreve como o repositório funciona hoje (v1.0) e, na segunda
parte, o que foi mudado em relação ao estado anterior do código (que não era
uma versão numerada — era o resultado de várias passagens de IAs diferentes
sem arquitetura consolidada).

## 1. Contexto do projeto

Este repositório é a etapa inicial de um TCC cujo objetivo final é um
analisador de qualidade de energia embarcado num microcontrolador ESP32. Para
treinar o classificador que vai rodar no ESP32, primeiro é preciso um dataset
rotulado de distúrbios de tensão — e é isso que este repositório produz.

A bancada física tem dois instrumentos, controlados via SCPI/VISA:

- **Fonte CA programável AMETEK MX30-3Pi** (California Instruments) — gera a
  tensão de alimentação e injeta os distúrbios.
- **Osciloscópio Keysight DSO-X 4034A** (série 4000X) — captura a forma de
  onda resultante.

Os dois são sincronizados por um cabo BNC: a saída de trigger da AMETEK
("Trigger Out") vai para o trigger externo do Keysight, de forma que o
osciloscópio sempre captura a partir do instante exato em que a fonte inicia
um distúrbio.

O produto do repositório são 20 classes de distúrbio (`experimentos.txt`),
cada uma gerando milhares de capturas de 200 ms (6000 amostras a 30 kSa/s),
salvas em `resultados/` como `.npz` (por classe e nível de SNR) + metadados
em `.jsonl`.

## 2. Sequência lógica de execução

```
mestre.py
  ├─ lê toda a configuração de variáveis de ambiente (porta, baudrate,
  │  limites de tensão/corrente, tensão/frequência base, SNR, seeds, ...)
  ├─ inicializar_instrumentos()
  │    ├─ modo SIMULADO (padrão): cria só um AmetekMX30(simulated=True),
  │    │  nenhum hardware é aberto
  │    └─ modo BANCADA (BENCH_MODE=1): abre a AMETEK via PyVISA serial,
  │       configura o baseline seguro (saída OFF), abre o Keysight via
  │       PyMeasure/VISA, configura canais/trigger/aquisição, autoriza e
  │       energiza a saída UMA VEZ para toda a bateria
  ├─ monta um Config (dataclass "burro", só dados) com fs_hz, points,
  │  grid_frequency_hz, base_voltage_rms, snr_levels_db, seeds, etc.
  └─ para cada classe 01..20 (em ordem):
       ├─ localiza o arquivo NN.py (em experimentos_nativos/ ou
       │  experimentos_waveform/ — nunca nos dois)
       ├─ carrega o módulo dinamicamente (importlib), com a pasta certa
       │  temporariamente no início do sys.path (pra ele achar seu comum.py)
       └─ chama run(fonte, osc, config)
            ├─ se osc is None (SIMULADO): laço de milhares de capturas
            │  usando só gerar(t, f0, capture_index, rng) — matemática pura
            │  em Python/NumPy, sem tocar hardware nenhum
            └─ se osc is not None (BANCADA): 1 captura real — programa o
               transiente nativo (PULSe/LIST/CSINe) ou sobe uma forma de
               onda arbitrária via TRACe, arma, dispara, lê do osciloscópio
       captura → aplica ruído AWGN por nível de SNR → grava .npz + metadata
```

O modo SIMULADO é o que realmente produz o dataset de treino (milhares de
capturas por classe, definido por `SIM_CAPTURES_PER_CLASS`, hoje 2000). O
modo BANCADA só produz `REAL_CAPTURES_PER_CLASS` (hoje 1) — é o
comissionamento físico, pra confirmar que a fonte e o osciloscópio realmente
reproduzem o que o modelo em Python prevê.

## 3. Estrutura de arquivos

```
ametek_orm.py            Driver (ORM) da fonte AMETEK MX30 — classe AmetekMX30

mestre.py                 TODA a configuração física + orquestração dos 20 experimentos
preflight.py               Validação progressiva em bancada real, sem energizar por padrão
                           (comunicação → trigger BNC → baixa tensão 5 Vrms)

experimentos_nativos/      Classes cujo distúrbio é um recurso NATIVO da AMETEK
    comum.py                helpers (janela, ruído AWGN, snr medida, salvar .npz,
                            executar_classe_nativa — laço genérico de captura)
    01.py .. 19.py          NORMAL, SAG, SWELL, INTERRUPTION, HARMONICS (misto),
                            FREQUENCY_DRIFT, DC_OFFSET

experimentos_waveform/     Classes que precisam de forma de onda arbitrária (TRACe)
    comum.py                mesmos helpers + onda_com_harmonicos/oscilacao_amortecida/
                            aplicar_entalhes + executar_classe_waveform
    06.py .. 20.py          FLICKER, NOTCH, TRANSIENT, OSCILLATORY_TRANSIENT e as
                            composições que envolvem essas

tests/test_offline.py      Testes sem hardware (ORMs com adapters/recursos "roteirizados",
                           todas as 20 classes, regressão do bug de ciclo/frequência)

setup_windows.ps1          Cria/atualiza o venv (env/) e instala requirements.txt
bench_config.ps1           ÚNICA fonte de variáveis de ambiente da bancada (porta, baudrate,
                           limites, probes) — sourced pelos outros .ps1
start_bench_windows.ps1    Fluxo guiado (-Stage Full/Communication/Trigger/LowVoltage/Run)
run_simulation_windows.ps1 Gera o dataset simulado (sem hardware)
package_windows.ps1        Empacota o repositório em .zip pra transporte
START_BENCH.cmd            Ponto de entrada único: chama start_bench_windows.ps1 -Stage Full

docs/                      Manuais SCPI da AMETEK e do Keysight (PDF)
resultados/                Saída: snr_XXdb/*.npz, corrente/*.npz, metadata/*.jsonl
```

Não existe mais nenhum arquivo de configuração ou de execução fora desses —
antes havia `experiment_config.py`, `experiment_runner.py` e `signal_models.py`
espalhando a mesma responsabilidade em 3 arquivos a mais (ver seção 6).

## 4. Programação orientada a objetos

O projeto usa OOP onde ela realmente ajuda — encapsular o estado e as regras
de segurança de cada instrumento físico — e não a força em lugares onde uma
função simples já resolve (por isso `mestre.py` é funções, não uma classe:
ele não tem estado próprio além da config, que é um dataclass).

### `AmetekMX30` ([ametek_orm.py](../ametek_orm.py))

Encapsula toda a comunicação serial/VISA com a fonte e, mais importante, os
**limites de segurança**: `max_voltage_rms`, `max_peak_v` e `max_current_a`
são passados uma vez no construtor (por `mestre.py`, a partir da config), e
os *setters* de `voltage`/`frequency`/`current_limit` recusam qualquer valor
fora desses limites (`ParameterOutOfBoundsError`). Um experimento nunca sabe
qual é o limite — ele só tenta setar um valor, e o objeto decide se é seguro.
Isso é o motivo de `configure_safe_baseline()` e `energize_baseline()`
existirem como métodos do objeto, e não como sequências de comandos SCPI
soltas em outro arquivo.

Também tem um **modo simulado** (`simulated=True`) embutido na própria
classe: os métodos de escrita/consulta desviam para um dicionário `_sim`
interno em vez de abrir uma porta serial. Isso permite testar toda a lógica
de programação de transientes sem hardware nenhum (é o que `tests/test_offline.py`
faz).

### `KeysightDSOX4034A` ([oscilloscope_orm.py](../oscilloscope_orm.py))

Mesma ideia do lado do osciloscópio: encapsula canais, aquisição, trigger
externo e a leitura/decodificação do bloco binário IEEE 488.2 devolvido pelo
`:WAVeform:DATA?`. `OscChannel` é uma subclasse de `pymeasure.instruments.Channel`
que mapeia os atributos de canal (escala, offset, acoplamento, unidade) para
os comandos SCPI correspondentes via descritores `Channel.control`.

### Injeção de configuração, não import

O `Config` de `mestre.py` é um `@dataclass(frozen=True)` — só dados, sem
métodos além de `capturas(simulated)`. `mestre.py` monta um `Config` uma vez
e passa como argumento pra `run(fonte, osc, config)` de cada experimento.
Nenhum `experimentos_nativos/NN.py` ou `experimentos_waveform/NN.py` importa
`mestre` — eles recebem tudo que precisam (fonte, osciloscópio, e os
parâmetros físicos) como parâmetro. Isso evita tanto a duplicação de config
(um único lugar define porta/baudrate/limites) quanto o import circular que
existiria se um módulo carregado dinamicamente por `mestre.py` tentasse
importar de volta o próprio `mestre.py`.

## 5. Os 20 experimentos

Cada classe é definida por dois efeitos possíveis: um **transiente nativo**
da AMETEK (mudança de nível real, capturada como a fonte de verdade reage) ou
uma **forma de onda arbitrária** via `TRACe` (array calculado em Python,
reproduzido ciclo a ciclo pela fonte). A escolha depende de quão rápido/
complexo é o fenômeno — ver seção 6.3 para a justificativa técnica.

| # | Classe | Pasta | Mecanismo na bancada real |
|---|--------|-------|----------------------------|
| 01 | NORMAL | nativos | sem distúrbio (STEP para o mesmo valor, só pra gerar o trigger) |
| 02 | SAG | nativos | `VOLTage:MODE PULSe` |
| 03 | SWELL | nativos | `VOLTage:MODE PULSe` |
| 04 | INTERRUPTION | nativos | `VOLTage:MODE PULSe` |
| 05 | HARMONICS | nativos (misto) | `FUNCtion:SHAPe CSINe` (4 níveis) + TRACe (nível de 30%, acima do teto do CSINe) |
| 06 | FLICKER | waveform | TRACe (modulação contínua 8-25 Hz) |
| 07 | NOTCH | waveform | TRACe (pulsos de 0,1 ms) |
| 08 | TRANSIENT | waveform | TRACe (pico único de 0,05 ms) |
| 09 | OSCILLATORY_TRANSIENT | waveform | TRACe (oscilação amortecida 300-2400 Hz) |
| 10 | SAG_HARMONICS | waveform | TRACe *(candidata a nativo — ver 6.4)* |
| 11 | SAG_FLICKER | waveform | TRACe |
| 12 | SAG_OSCILLATORY_TRANSIENT | waveform | TRACe |
| 13 | SWELL_HARMONICS | waveform | TRACe *(candidata a nativo)* |
| 14 | SWELL_OSCILLATORY_TRANSIENT | waveform | TRACe |
| 15 | HARMONICS_FLICKER | waveform | TRACe |
| 16 | INTERRUPTION_HARMONICS | waveform | TRACe *(candidata a nativo)* |
| 17 | NOTCH_OSCILLATORY_TRANSIENT | waveform | TRACe |
| 18 | FREQUENCY_DRIFT | nativos | `FREQuency:MODE LIST` |
| 19 | DC_OFFSET | nativos | `SOURce:MODE ACDC` + `VOLTage:OFFSet` |
| 20 | INTERHARMONICS | waveform | TRACe |

Em todos os casos, o **dataset simulado** (as milhares de capturas de
treino) vem sempre de `gerar(t, f0, capture_index, rng)` em Python — a
distinção nativo/TRACe só importa para a única captura de comissionamento em
bancada real.

## 6. O que mudou nesta versão

O estado anterior do código (não versionado, resultado de várias passagens de
IAs diferentes) tinha a arquitetura pretendida (dois ORMs + `mestre.py`) mas
com a responsabilidade de config e execução espalhada em mais três arquivos
(`experiment_config.py`, `experiment_runner.py`, `signal_models.py`), os 20
`experimentos/NN.py` reduzidos a wrappers vazios que só repassavam o ID pra
uma função em outro arquivo, e um bug real de física corrompendo a forma de
onda entregue à fonte. Nada disso foi commitado antes desta versão.

### 6.1 Refactor de arquitetura

- **Três scripts centrais.** `experiment_config.py` e `experiment_runner.py`
  foram absorvidos por `mestre.py`; `signal_models.py` foi dividido entre os
  `comum.py` de cada pasta de experimentos (matemática de sinal) e os
  próprios `NN.py` (a fórmula de cada classe, que antes vivia escondida num
  `if/elif` de 20 ramos em outro arquivo).
- **Experimentos autocontidos.** Cada `experimentos_nativos/NN.py` e
  `experimentos_waveform/NN.py` define, no próprio arquivo, o que aquela
  classe é (`gerar()`) e como ela roda (`run()`) — sem precisar abrir outro
  arquivo pra entender o que a classe 07 faz.
- **Divisão nativos/waveform.** Reflete uma mudança de método, não só de
  arquivo: SAG/SWELL/INTERRUPTION/parte de HARMONICS/DESVIO DE FREQUÊNCIA/DC
  OFFSET passaram a usar os modos de transiente nativos da AMETEK (`PULSe`,
  `LIST`, `CSINe`, documentados no manual SCPI, cap. 6.4) em vez de um array
  pré-calculado — o osciloscópio passa a capturar a resposta física real do
  regulador da fonte, não uma aproximação.
- **Saída energiza uma vez.** A fonte liga (`energize_baseline()`) uma única
  vez no início da bateria inteira e nunca mais desliga entre capturas —
  antes, cada captura desligava e religava a saída (motivado por um bug de
  firmware específico que na verdade só exigia resetar `FUNCtion:MODE`, não
  ciclar `OUTPut`). Confirmado contra o exemplo oficial do manual (cap. 6.4.2),
  que liga a saída uma vez e dispara vários transientes em sequência.
- **Pré-trigger no osciloscópio.** `configure_acquisition()` ganhou
  `pre_trigger_s`, usando `:TIMebase:POSition` do Keysight pra capturar
  "normal → distúrbio → normal" numa única aquisição, sem precisar de atraso
  programável na fonte (que não existe — `PULSe` dispara no instante do
  trigger).
- **Gravação em NumPy (`.npz`) em vez de CSV.** Elimina a escrita linha a
  linha via `csv.writer` e a repetição de `classe`/`id_captura` por amostra;
  cada classe/nível de SNR vira um array `(capturas, pontos)`. Escrita
  atômica preservada (`.npz.part` → `os.replace`).
- **PowerShell consolidado.** `run_preflight_windows.ps1` e
  `run_bench_windows.ps1` viraram o parâmetro `-Stage` de
  `start_bench_windows.ps1`; `gerar.sh` (que regenerava os wrappers vazios da
  pasta `experimentos/` antiga) foi removido — não faz mais sentido, cada
  `NN.py` agora tem conteúdo real e específico.

### 6.2 Bugfix: ciclo/frequência na AMETEK (o mais importante)

`AmetekMX30.POINTS_PER_CYCLE` estava fixo em `600` amostras — o que só
corresponde a um ciclo fechado da onda a **50 Hz** (`30000/600`). O padrão do
projeto é **60 Hz** (rede brasileira). A 60 Hz, um pedaço de 600 amostras
(20 ms) é 1,2 ciclos, não um ciclo fechado — e cada `TRACe` enviada à fonte
precisa representar exatamente um ciclo (o manual exige 1024 pontos = 1
ciclo por forma).

Efeito prático: ao normalizar um pedaço que não fecha um ciclo (forçando
média zero, como uma onda CA de verdade deveria ter), o pico calculado
infla artificialmente — medido em ~15% de erro para uma senoide limpa de
60 Hz — e a reprodução física tem descontinuidade de fase a cada troca de
passo do `LIST` (dwell fixo de 20 ms não é um número inteiro de períodos a
60 Hz). Isso é uma causa plausível para a baixa resolução observada nos
testes em 5 Vrms.

Correção: `program_capture()` agora calcula `pontos_por_ciclo` e o número de
ciclos dinamicamente a partir da `frequency_hz` real programada
(`FS_HZ / frequency_hz`), e o `SOURce:LIST:DWELl` passa a ser exatamente
`1 / frequency_hz` (um período exato) em vez do valor fixo `0.02`. A 60 Hz
isso dá 12 ciclos de 500 amostras; a 50 Hz continua 10×600 (idêntico ao
comportamento antigo, que só "funcionava" por coincidir com esse caso).
Erro de pico medido após a correção: ~0,0007%.

Coberto por `tests/test_offline.py::AmetekTests::test_cycle_count_matches_grid_frequency_not_hardcoded_50hz`.

### 6.3 Outros ajustes de correção

- `arm_transient()` validava o número de pontos do `LIST` contra o valor
  fixo `"10"` — agora usa o número real de ciclos da última
  `program_capture()` (`self._last_cycles`).
- `TRACe:DELete:ALL` (limpar formas de usuário) exige `OUTPUT OFF` — como a
  saída agora fica ligada durante toda a bateria, isso virou um método
  explícito (`clear_all_traces()`) chamado uma vez antes de energizar, em vez
  de uma tentativa condicional dentro do laço de captura.
